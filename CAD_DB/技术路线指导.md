# 技术路线指导

## 项目概况
基于数据库的协作式 CAD 系统（DB-CAD），现开发重点在于多人协作部分，存在A、B两个客户端和一个服务端，通过fastapi进行连接，A 端画布编辑 ACIS 几何体，通过push按钮上传到服务端（bridge，也就是一个静默的DBCAD客户端），服务端进行向neo4j图数据库/postgreSQL关系数据库进行数据存储并向B客户端进行远程版本号更新广播，B 端通过pull按钮拉取并重建。

## 模式机制与目的阐述

### 实现目的：

我希望mode1和mode2能做成两条增量的路径，增量的意思是区别于mode0的全量sat文本数据传输，主要表现为以下几点：

1.网络传输压力小，对于整个画布的所有实体来讲，通过网络（fastapi）传输整个sat文本是及其耗费资源的，也是我们不想看到的，所以我们希望网络传输层能仅进行当次的修改的几何信息的传输（当次的意思即本版本基于上次版本的修改，包括实体添加和删除或者后面要考虑的变换）

2.对本地尚未提交的版本的本地修改友好，mode0的逻辑会产生拉取一个版本直接覆盖该客户端的画布的情况，而mode1和mode2的增量的路径即会保留本地的修改，这一点为后续的冲突合并打下了基础

mode1和mode2也有一些区别，具体如下：

1，mode1我希望的存取路径主要依赖于neo4j图数据库，本项目已经实现过neo4j的增量存取逻辑，我进行阅读即对当前的画布上的acis实体进行BFS遍历然后将每个实体作为一个节点，同时保留实体间的关系作为边，共同存在一个子图中，这个子图实际上也就是一个版本，也有对应的增量逻辑的实现。

2.mode2我希望的存取路径主要依赖于postgreSQL关系数据库，目前尚未想好对应的实现路径，后续进行开发

**协作面板中有一个模式选择下拉框，决定使用哪个 mode 进行 Push 和 Pull 作为一个整体单元协同工作：**

### Mode0（SAT 全量）：

- **Push**：当前画布所有实体的完整 SAT 文本 → HTTP POST models → bridge 存储
- **Pull**：B 客户端点击 Pull → WebSocket `sync_now` → `entity_graph_saved` 广播 → 全量 restore 覆盖画布
- **特点**：简单可靠，但网络传输量大，会丢弃本地未推送修改

### Mode1（Neo4j 增量）：

**粗略大体逻辑**：

- 单机时代（`api_save_neo4j` / `api_restore_neo4j`，access.cpp 第 4055/5543 行）：一个客户端 + 一个 Neo4j，用 ACIS 自带的 `DELTA_STATE / BULLETIN_BOARD` 自动分离每次相对上次的修改，BFS 遍历 ACIS 实体 → 每个实体（body/lump/shell/face/loop/coedge/edge/vertex/...）作为一个 Neo4j 节点，实体间的关系（body_lump / lump_shell / shell_face / face_geometry / ...）作为 Neo4j 关系边；每次 push 创建 `(:generation {b:i})` 节点，节点属性 `{c: generation_id, d: latest_generation_id}` 标记所属版本，`generation_prev_ptr` / `generation_new_ptr` / `generation_old_ptr` 串起版本链；restore 时沿 generation 链回放。

- 联机 mode1：现在**不能再用 ACIS 自带版本板 board**（每个客户端是独立 ACIS 进程，DELTA_STATE 不互通，bridge 进程的 board 也永远是空的）。设计目标是把 bridge + Neo4j 视为一个**等价的单机 Neo4j 存取对**——bridge 跑 DBCAD 二进制、用同一套 `api_save_neo4j` / `api_restore_neo4j` 维护 generation 链——区别只是"存取什么"由 fastapi 转过来的其他客户端决定。

- bridge 是静默 DBCAD 客户端：不开 GUI、不显示 GLWidget、不响应 addEntity UI 事件；但它的 ACIS 内核、Neo4j 客户端、版本历史管理与 GUI 客户端完全一致。

### Mode1 开发预期（最终形态 / 当前阶段目标）

#### 总体原则

1. **传输层不用 SAT 文本**：A ↔ bridge ↔ B 之间传的是 `entity_graph JSON`（即 `entity_graph_serializer.cpp::serializeACISEntityGraph` 输出的节点-关系图），不是 SAT。A 客户端从 ACIS ENTITY 序列化成 JSON，B 客户端从 JSON 反序列化成 ACIS ENTITY。bridge 不参与 ACIS 序列化/反序列化，只做 JSON merge + Neo4j 存取。

2. **服务端做增量 diff**：bridge 维护完整 `entity_graph JSON` 状态，收到 A 推送的 delta JSON 后按 uuid 集合差合并，而不是把 SAT restore 回 ACIS 内存再重写 Neo4j。

3. **Neo4j 存完整 entity_graph JSON + per-version 历史**：每个 version 是当前画布完整 entity_graph JSON 的快照（不是只存变更），存到 Neo4j 的 `(:entity_graph_version {b: project_id, c: version, json_text: '...'})` 节点。这样任意历史版本都能还原，不需要连续应用增量。

4. **基于 UUID 的协作语义**：每个 body 有稳定 UUID（Qt 层生成，存在 `entityIndexToUuid` 里）。Push 携带 uuid 列表、Pull 端用 uuid 做集合差合并、删除/修改都通过 uuid 匹配。

5. **服务端不参与 ACIS 几何**：bridge 进程只是 Neo4j + JSON 处理的中转。它不需要 restore SAT，不需要 `api_save_entity_list_neo4j` 那套 ACIS 几何 → Neo4j 节点属性的转换。

#### 当前阶段（过渡期）的妥协

由于 `deserializeACISEntityGraph` 当前只支持基础几何（PLANE/SPHERE/CONE/TORUS/STRAIGHT/ELLIPSE/HELIX），SPLINE/INTCURVE 等复杂类型会 fallback。考虑到现有 A 客户端推送仍然用单 body SAT 段（`serializeBodyToSat`）、服务端中间要 restore SAT 拼 ACIS 内存才能写 Neo4j，**当前过渡方案保留 SAT 作为传输载体**，但 bridge 内部做完 ACIS 内存合并后，需要：
- 把 uuid 存到 Neo4j body 节点属性（关闭 uuid 持久化链路）
- 生成正确的 SAT header 给客户端 pull（保证 restore 出来有拓扑）

#### A 客户端 Push（过渡期实现）

```json
payload = {
  "author": "<name>",
  "base_version": 2,
  "delta_uuids": ["uuid-A", "uuid-B"],
  "delta_sat_segments": ["<单 body SAT-A>", "<单 body SAT-B>"],  // 带 schema header
  "removed_uuids": ["uuid-C"]
}
```

→ HTTP POST `/projects/{id}/delta`

**Bridge handleSaveDelta (`handle_save_delta_to_neo4j`)**：

1. 从 Neo4j 读取 base_version 时的完整 `ENTITY_LIST`（走 `api_restore_entity_list_neo4j_part`）。
2. 对 `delta_sat_segments` 逐段 `acis_restore_entity_list` 合并到内存 ENTITY_LIST。
3. 按 `removed_uuids` 在内存里 `api_del_entity` 对应 body。
4. 维护 `body_ptr_to_uuid` 映射：新增 / 修改 body 时把 uuid 写进 map。
5. 调 `api_save_entity_list_neo4j_part` 重建整张 part 子图（含 topology 节点 / 关系）。
6. **关键**：`api_save_entity_list_neo4j_part` 写完后，按 entity_list 中 body 的顺序，bolt 补一次 `MATCH (n:part {b:$Y})-[r:part_entity_ptr]->(b:body) WHERE id(b) IN $B SET b.uuid = $U` 把 uuid 写进 body 节点属性（这是闭合 uuid 持久化链路的核心）。
7. 更新 `part.version = base_version + 1`。
8. 返回新版本号。

#### B 客户端 Pull

→ HTTP GET `/projects/{id}/delta?base_version=2`

**Bridge handleGetDelta (`handle_get_delta_from_neo4j`)**：

1. 读 `latest_version = part_node.version`。
2. 若 `base_version >= latest_version`，返回空 delta。
3. 从 Neo4j 读取 body 节点 + uuid 属性（`RETURN id(b), b.uuid ORDER BY r.b`，uuid 不为空才纳入）。
4. 从 Neo4j restore 完整 `ENTITY_LIST`（走 `api_restore_entity_list_neo4j_part`）。
5. 对每个 body **单独** save 成单 body SAT 段。**关键**：必须在 save 前调 `api_set_int_option("sequence_save_files", 1)` 写 schema header，并用 `text_mode=1`（不是 2）；外面套 `API_NOP_BEGIN/END`。
6. 返回：
   ```json
   {
     "version": 3,
     "delta_bodies": [{"uuid": "uuid-A", "sat": "<单 body SAT 带 schema header>"}, ...],
     "deleted_uuids": []
   }
   ```

**B 客户端本地合并（`pullMode1Delta`）**：

1. `pull_added = remote_uuids - local_uuids` —— restore 并 addEntity。
2. `pull_removed = local_uuids - remote_uuids` —— 检查未推送修改后删除。
3. **关键**：restore 后做 topology sanity check：必须 `is_BODY(el[0])` 且 `el[0]->lump() != nullptr` 且 `api_get_faces` / `api_get_edges` 返回非零，否则视为 restore 失败直接 skip（避免空壳 body 进入画布）。

### Mode2（PostgreSQL 增量）：

使用A客户端push推送的时候发送的是经过BFS遍历当前画布上在上一次push的基础上的的增加的或减少的修改实体的图序列化json文本，服务端按照增量逻辑将单个实体json存在postgreSQL关系数据库的一行中，B客户端pull拉取之后通过图反序列化进行重建即可
