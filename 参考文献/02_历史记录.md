History Management Functions with Part Manager
The calls to api_part_start_state and api_part_note_state must be strictly paired regardless of any potential errors. Start state and note state are paired
by the use of a static counter. If a note state were skipped because of an error, the counter would be off by one and subsequent states would not be noted. One way to

achieve this is illustrated in the example below.

```cpp
int depth;
api_part_start_state(depth);
result = api_do_stuff_1(args);
check_outcome(result); // If result is not ok,
// jump to API_END
// Alternate style of using check_outcome
check_outcome(api_do_stuff_2(args));
// Tell the part manager and graphics what happened
record_entity(new_top_level_entity);
update_entity(modified_top_level_entity);
api_part_note_state(outcome(API_SUCCESS), depth);
```

If an error occurs in the above example, it will be caught by API_END. The api_part_note_state is always called regardless of error. Note that the outcome is
checked before recording or updating entities, so the part manager and graphics do not see anything bad. The amount of history checking is controlled by the global
You can also use the EXCEPTION_BEGIN/TRY/CATCH/END macros with api_part_start_state in the EXCEPTION_BEGIN block and
api_part_note_state in the EXCEPTION_CATCH( TRUE ) block.


The Kernel has a set of APIs allowing advanced part management independent of the Part Management Component. This permits roll back without using the Part
Because Part Management uses the Kernel Component APIs, any use of the roll portions of the Part Management could interfere with tasks performed by the Kernel
APIs. Even innocuous APIs such as api_pm_save_part and api_pm_load_part could cause problems, because they close delta states and could create new ones.
Generally speaking, API functions that begin with "api_pm_" should be avoided. These functions were written to support the Scheme AIDE and are not for general use.

api_set_default_history can be used to set the active history stream: that is, the history stream on which bulletins will be created. If a delta state is created on
one history stream (the currently active history stream), it can be moved to another history stream using api_remove_state and api_add_state. After noting
the state, remove it from the default history stream and add it to the stream it should belong to. If a delta state contains bulletins from more than one history stream, it
is said to have mixed history. The bulletins of a delta state with mixed history can be distributed to the correct history streams using
api_distribute_state_to_streams. The behavior of this API function can be tailored by deriving a new class from the StreamFinder class. If a history
stream will contain mixed history, you must call HISTORY_STREAM::set_distribute_flag(TRUE) so that the bulletins can be subsequently distributed.

### Example 3

The following code snippet demonstrates how api_distribute_state_to_streams can be used to distribute the bulletins of a DELTA_STATE to multiple
history streams. In this example two bodies are created on two history streams. Then an entity-entity distance calculation is performed on a third history stream. This
operation causes bounding boxes to be calculated for the two bodies. api_distribute_state_to_streams is used to distribute the bulletins from this history
stream back to the history streams on which the bodies were created. Because mixed history streams exist in this example (when the two bodies are modified on the
third history stream), HISTORY_STREAM::set_distribute_flag(TRUE) must be called for the third history stream.

```cpp
HISTORY_STREAM::set_distribute_flag(TRUE)
```

Important: api_distribute_state_to_streams requires that the bulletins on the given DELTA_STATE must be separable or distributable. If the
two bodies had been united on the third history stream, the bulletins of the DELTA_STATE could not have been distributed back to the history streams
containing the original two bodies, because the bodies would have been combined by the unite operation into a single entity.
This example also provides a minimal StreamFinder. The implementation of findStream for this class is fairly simplistic, but it is sufficient for this example. It only
needs to determine the history stream for a given entity. In this case it is sufficient to return the history stream of the top level entity containing the given entity. This
function could also be used to determine if the entities had been combined by comparing the history stream of the given entity with the history stream of its top level
entity. If these history streams were different and the entity had not been created on the DELTA_STATE being distributed, it would indicate the entities had been
combined. The implementation of findStream is application-specific.

Disabling History
History is not explicitly enabled or disabled. It is effectively enabled simply by making calls to functions to perform required tasks. ACIS provides two levels of disabling
history.
With api_logging(FALSE), bulletins and delta states are still created, but they are kept only long enough to support error recovery. Application logging (sometimes
called api_logging) can be set in Scheme AIDE using the global option api_set_stream_logging and in Scheme AIDE using history:set-logging.

With set_logging(FALSE), no bulletins are created, but bulletin boards and delta states are still created. ACIS operations and functionality that examine the changes
made during an operation may fail or produce unexpected results. Modeling errors cannot be recovered unless the application developers provide their own mechanism.
Because of the inability to recover from errors, it is strongly recommended to use api_logging, instead of set_logging, if an application needs to disable history
logging. In Scheme AIDE, the logging flag is set using roll:set-logging.
When history is disabled, you must be careful about the use of API_BEGIN/API_END and you should call api_note_state periodically to clean up memory used
by empty bulletin boards.
Important: If history is disabled, you must be sure all ENTITYs are deleted by calling either ENTITY::lose or a higher level API function that calls
ENTITY::lose for you. If any ENTITYs are not lost, they will cause memory leaks.

## 历史之流 · History Stream

> 来源：`history_stream.pdf`

A History Stream is the highest level construct in the core ACIS history mechanism. A history stream contains
one or more delta states and contains all of the changes to one portion of an ACIS model. An ACIS model may
have one or more history streams. (As an example, an assembly modeling application might choose to dedicate
one history stream for each sub-assembly, or each individual component, in the model.) The history streams
for a given model can be saved with the model in its save file. Later, this entire structure can be restored,
permitting roll back to any point in the development of this model.

### Overview

The history mechanism maintains a data structure that can be viewed as hierarchical in nature. At the lowest
level is the bulletin. A bulletin records a change to a persistent model entity. A bulletin board maintains a series
of bulletins. A bulletin board represents the smallest unit of history that can be rolled back. If an error occurs
the current bulletin board will be rolled back. This prevents the model from being corrupted by a failed or
incomplete operation. A delta state maintains a sequence of one or more bulletin boards. A delta state is the
smallest unit of history that can be rolled back or forward, or completely removed from the history data
structure, by an application. A delta state typically equates to an operation from an end user's perspective. A
history stream maintains one or more delta states, representing the most recent history for the model. It is
possible for an application to maintain more than one history stream. This allows different portions of a model
to be managed separately. For instance, if there were multiple parts in an assembly, each part could have its
own history stream, which would allow "undo" and "redo" operations to be performed on one part without

affecting other parts in the model. Alternatively, each part could be maintained in a separate model, and the
application could distinguish between part modeling and assembly modeling operations. Bulletins, bulletin
boards, delta states, and history streams are the basic constituents of history mechanism. Other (optional)
classes that provide higher level functionality include the history manager, the part manager, the entity
“ ” “ ”

### Bulletin

A bulletin is the lowest level element in the history mechanism. A bulletin records the creation, modification,
or deletion of an entity during an operation.

### Bulletin Board

A bulletin board maintains the bulletins representing a single operation. A bulletin board contains the set of
model changes that would be rolled if an error occurred during the operation. Bulletin boards may be nested
(that is, a bulletin board may exist within another bulletin board) temporarily. This allows a sub-operation to be
undone if it fails, without causing the overall operation to fail. This is sometimes called failsafe behavior.

### Delta State

Delta
A delta state contains one or more bulletin boards and represents changes that were made between two

states. Rolling backward or forward occurs between states. A delta state represents the smallest group of
changes that you can undo or redo.

saved with the model in its save file. Later, this entire structure can be restored, permitting roll back to any
point in development.

### History and Roll in Assembly Modeling

ACIS Assembly Modeling is designed to support history and roll operations on both part and assembly entities.
(Refer to Entity Managers in Assembly Modeling for a definition of "part entities" and "assembly entities".)
Assemblies, model references, and properties are implemented using subclasses of ENTITY, and thus,
participate in history and roll.
Managing history streams and roll operations are "part mode" operations; they are the responsibility of the
application document(s) bound to the history stream. (Refer to nested_activate_vf method on the entity
manager which owns the entities being acted upon.
ACIS Assembly Modeling supports independent roll of model contents; every asm_model object can have an
independent history stream bound to its corresponding application document. Multiple models may also be
bound to the same history stream, up to having all models share the same history stream; most customers will
want to associate a unique history stream with each model.
Models may be saved to ASAT with history, analogous to how entity lists may be saved to SAT with history with
one subtle difference. If an ASAT file which was written with history contains models which share a history
stream, then the corresponding models must share a stream when the ASAT file is read, even if history is not
restored. This is different from the behavior of SAT, where the presence of history data in a file does not affect
the result of a read operation in which history restoration is turned off.

The fact that ACIS assemblies are distributed across multiple histories streams (associated with the models
used by the assembly) can lead to some behaviors and limitations which are non-intuitive to developers used
to working in part modeling mode:
Assembly modeling handle objects, that is, entity handles, component handles, and component-entity
handles have two states: "valid", where they refer to live entities, and "invalid", where at least one of the
entities to which they refer (directly or indirectly) has been deleted. If the deleted entity(s) is brought back
to life (undeleted) by a roll operation, then the invalid handle becomes valid again. The validity of a handle
can be queried calling its is_valid() method.
